## 1. Контракт

- **Изменено:** Q `[B,Sq,Hq,D]` (bshd — родной формат MSA и inference-движков);
  partial O `[B,Sq,16,Hq,D]`. Combine читает по новому адресу.
- **Не изменено:** K/V `[B,Hkv,Skv,D]`, LSE `[B,Hq,Sq,16]`, final O `[B,Hq,Sq,D]`,
  FP32 LSE, допуски, exact-гарантии.
- TMA-путь — для G ≥ 8 (box из G строк должен начинаться на границе
  1 KiB swizzle-атома). G1/G2/G4 идут прежним cp.async/bulk-путём round9 с
  новым индексом partial — потому на них выигрыша нет (см. §3).
- Код изолирован в `optimization_round11`; hashes 191 файлов прежних
  раундов проверены.

## 4. Что именно реализовано

**Gather Q через TMA.** 2D tensor map над Q как `[B·Sq·Hq строк, 128]`
(bf16, swizzle 128B, box `{64, G}`). Issuer группы читает id токенов из
query_map и выдаёт 2 TMA на токен (16 на chunk при G16) плюс
`mbarrier.arrive.expect_tx` на суммарные байты реальных токенов;
padding-токены пропускаются. Q ложится в тот же swizzled layout, который
раньше 128 потоков собирали 2048 `cp.async` с 64-битной адресацией.
`q_ready[g]` — mbarrier с `complete_tx`; compute-группа ждёт его перед QK.

**Epilogue через TMA store.** Стейджинг в 128B-swizzled layout
(панели по 128 B на строку; `chunk ^ (row & 7)` — 16-байтные STS восьми
соседних строк покрывают все 32 банка), `fence.proxy.async` каждым
потоком → `bar.sync` группы → issuer выдаёт box'ы `{64|32 колонки, G строк}`
на токен: BF16 — один проход, 16 TMA store на chunk; FP32 — четыре прохода
по одной панели через две чередующиеся половины стейджинга
(`wait_group.read 1` — ожидание только стора двухпроходной давности).

**Combine11** — та же арифметика и порядок накопления, другой адрес
partial; `out`/`out_lse` побитно совпадают.

Регистры: TMA-специализации 237 (FP32/BF16), fallback 165; spills нет;
SMEM 196 KiB; TMEM 512.

## 5. Почему FP32 не ускорился

Разница FP32−BF16 у tma (1.598−1.177 = 0.42 ms) больше, чем у split
(0.29): FP32-epilogue через TMA дороже строкового ровно настолько,
насколько дешевле стал gather. Попытка убрать ожидание между проходами
(run 2, чередующиеся половины стейджинга) ничего не изменила — FP32-путь
упирается в объём записи 4 GiB partials (round7: `no_store` −32%), а не в
инструкции; TMA меняет инструкции, не байты. Exact-путь остаётся `split8`.

## 6. Проверка корректности

Каждый кандидат в обоих кандидатных вызовах и в подтверждении:
- suite 16 случаев + `resident_tail` против FP32 oracle, прежние допуски —
  те же максимумы, что у родителей (0.00780 / 0.01349, LSE 2.67e-5);
- **23 побитных сравнения** с родителем через view `[B,Hq,Sq,16,D]` —
  все нули; 3 Graph replay со сменой IDs/Q/V — нули, `exact_coverage`;
- 11 confirmation-форм: partial (через view), final O и LSE побитно равны
  первому варианту того же dtype;
- memcheck/synccheck: `ERROR SUMMARY: 0 errors` во всех трёх вызовах;
- локально 8 structural tests (арифметика round9 дословно, индексы
  token-major в gather/epilogue/Combine, swizzle-формула и банки, порядок
  TMA-протокола, fallback для G<8).

## 8. Решение

- **`tma16_bf16` (variant 2) — новый BF16-путь по умолчанию** для G ≥ 8
  и independent/hot масок: 1.503 ms; `tma8_bf16` — ровнее на shared/identical.
  Оба требуют Q в `[B,Sq,Hq,D]`.
- **Exact-путь — по-прежнему `split8` (round9)**: token-major layout ему не
  помогает; `tma8` эквивалентен по скорости и оставлен как exact-вариант
  для тех, кому нужен единый layout.
- До MSA на его маске (1.300) остаётся 1.16×; main bf16 1.11 против их
  forward 0.88. Следующие резервы — persistent (per-task накладные, см.
  round9/10) и store-warpgroup поверх TMA-путей (round10 показал, что при
  дешёвом gather/epilogue store-группа перестаёт быть issue-bound).
