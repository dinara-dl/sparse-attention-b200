# Текущий p03 против FA4: результаты

Дата: 18 сентября 2026. Все результаты ниже получены заново на B200 текущим
`sparse/02_gqa_block_sparse.cu` через основной `stage_functions("p03")`.
Старые числа `s10` не перенесены и не смешаны с этим экспериментом.
CUDA-код, wrapper, индексер, прежние результаты и черновик блога не изменены.

## Главный вывод

- При независимых списках соседних Q128 наш p03 быстрее лучшего проверенного
  FA4 sparse примерно в **1.14×** на 4K, 8K и 16K.
- При попарно одинаковых списках соседних Q128 **FA4 sparse быстрее примерно
  в 1.12×**. То есть прежний вывод о зависимости победителя от маски подтверждён
  уже текущей версией кода.
- При 16K наш kernel с готовыми IDs быстрее FA4 dense примерно в **6.38×**
  на независимой маске. Но он обрабатывает только 12.5% связей; одинаковое качество
  с dense здесь не проверялось, цена выбора блоков не включена.
- На 2K, когда TopK16 выбирает все блоки, наш kernel проигрывает FA4.

## Условия

B200, `B=2`, `Hq/Hkv=16/1`, `Sq=4096`, `D=128`, BF16, non-causal forward.
KV-блок128, TopK16: каждый query обрабатывает 2048 выбранных ключей.
Списки общие для Q128 и GQA-группы; разные Q128 могут иметь разные списки.
Порядок ID в performance-тестах — по возрастанию номера блока.

Наш backend: текущий **p03**, не прежний s10. SHA-256 CUDA:
`0b224b2ce92d2192a5dd745cb607e04a73fb4010ebdc7373e3ab350d28268127`.
FA4 pinned commit: `ce088ab9ce0fc0434dcd8afa0a791da9fcc3a820`.

Время в **микросекундах**, меньше — лучше. Медиана трёх раундов для каждого
seed17/29/41, затем медиана трёх seed. Отношения времени сначала вычисляются
внутри каждого seed на одном GPU, затем агрегируются. Поэтому отношение
округлённых итоговых latency может немного отличаться от приведённого speedup.

## Независимые списки Q128

| Skv | Выбрано блоков | Наш p03 | FA4 sparse | FA4 dense | FA4 sparse / наш | FA4 dense / наш |
|---:|:---:|---:|---:|---:|---:|---:|
| 4096 | 16/32 | 137.81 | 157.00 | 228.20 | 1.139× | 1.656× |
| 8192 | 16/64 | 138.06 | 157.23 | 448.67 | 1.138× | 3.247× |
| 16384 | 16/128 | 140.27 | 159.95 | 894.60 | 1.139× | 6.379× |

Лучший из проверенных FA4 sparse здесь — **Q1, PackGQA off**.
Победитель одинаков на всех трёх seed каждой длины.
Независимые случайные списки могут пересекаться; это не специально disjoint-маска.

## Одинаковые списки соседних Q128

Одинаковые списки задаются для пар (0,1), (2,3), ...; это не один список на всю
последовательность. Q/K/V для каждого seed совпадают побитно с independent-случаем.

| Skv | Наш p03 | FA4 sparse | FA4 dense | FA4 sparse / наш |
|---:|---:|---:|---:|---:|
| 4096 | 136.90 | 122.08 | 227.79 | 0.892× |
| 8192 | 136.99 | 121.83 | 449.02 | 0.889× |
| 16384 | 138.76 | 123.65 | 894.35 | 0.891× |

Здесь лучший проверенный FA4 sparse — **Q2, PackGQA off**. Победа FA4 сохраняется
на всех трёх seed. Наш schedule организует reuse между двумя query-heads одного
Q128; этот benchmark не добавляет ему reuse между соседними Q128.
Подробный sweep промежуточного overlap в этот эксперимент не входил.

## Контроль без разрежения

При Skv2048 доступны ровно 16 блоков, поэтому TopK16 выбирает их все.
Sparse и dense математические маски здесь совпадают.

| Наш p03 | FA4 sparse | FA4 dense |
|---:|---:|---:|
| 136.63 | 120.12 | 118.15 |

Этот случай показывает: сам sparse-интерфейс не гарантирует ускорения, когда
нет пропуска вычислений. Разрыв нельзя целиком объяснить ценой metadata без
дополнительного профилирования: реализации имеют разные schedules и pipelines.

## Честность сравнения

- Четыре FA4 sparse-конфигурации: Q1/Q2 × PackGQA on/off. Q1 — явно обозначенный
  Python launch override существующего FA4 kernel, а не стандартный dispatch.
- Q2 использует прежний проверенный **vector32 exact-mask adapter**. Intersection
  блоков — full, остальные блоки union — partial с точной маской. Маска не огрубляется.
- Четыре FA4 dense-конфигурации: PackGQA on/off × 2CTA auto/disabled.
  Лучший dense в этой сетке — PackGQA off, 2CTA disabled.
- Таблицы используют лучший результат среди проверенных конфигураций, не заведомо
  медленный default и не заявление об исчерпывающем autotuning.
- Каждый sparse backend получает одинаковые логические Q/K/V и разрешённые связи.
  Предпочтительные layouts и FA4 metadata подготовлены вне таймера.
- Один GPU-запуск на длину: девять backend, оба pattern и три seed измеряются
  вместе. Разные длины могут выполняться на разных физических B200.
- CUDA Graph: восемь вызовов, warmup250ms, measurement1000ms, три раунда.
  Начальный backend ротируется: каждый начинает один раз за три раунда × три seed.
- Это steady-state same-buffer attention-only, не cold-cache serving.
  Индексер, генерация IDs, layouts, allocations, compilation и reference исключены.

## Проверки и устойчивость

17 CPU-тестов прошли: четыре новых protocol/mask теста, три существующих
metadata-теста и десять тестов основной progression.

GPU: **пять полных correctness-сценариев**, затем **21 измеряемый случай**
(семь сочетаний length/pattern × три seed) и **567 отдельных round timings**.
Каждый backend проверен по полному независимому FP32 QK/softmax/PV reference,
TF32 off, до измерений и после CUDA Graph replay. Перед replay outputs заполняются NaN.

Gate включает нечётное число Q-тайлов, disjoint-маски, обратный порядок IDs,
несколько GQA-групп, scale4 и несколько итераций persistent CTA.

- Максимальная abs error нашего p03 на gate: **0.01999950** (включая scale4).
- На фактически измеренных scale1-входах: **0.00162134**.
- Максимальная abs error среди всех backend и сценариев: **0.02260780**.
- Заранее установленный допуск: `abs(error) <= 0.02 + 0.02*abs(reference)`.
  Это combined absolute/relative criterion, не отдельный абсолютный потолок 0.02.
- Максимальный min/max разброс трёх раундов относительно медианы: **1.195%**.

Это correctness на синтетических данных и наблюдаемая повторяемость timing,
не проверка качества модели и не доказательство отсутствия всех аппаратных гонок.
Compute Sanitizer и Nsight в эту задачу не входили.

Все пять Modal-запусков завершились успешно и сохранили `timeout=8*60`.
Суммарное время удалённых функций — около 814 секунд; это не точный billing time.
Хэши текущих main sources, экспериментального harness и установленного FA4
проверяются до каждого запуска; для каждого сохранены исходники и call ledger.
